# Code Review 工作流

交付能讓作者採取行動的審查結果，重點是會影響正確性、安全、資料或維運的問題。沿用專案的審查格式、風險規則與既有測試工具。

## 確認範圍與風險

- 先讀適用的專案指引，確認 base／head、diff 與變更意圖。使用者未指定範圍時，查看目前工作區差異並說明涵蓋範圍，不自行納入其他未相關檔案。
- 只要求審查時維持程式碼不變；已要求修正時在授權範圍內處理，不將審查擴大成重構或發布。
- 根據實際行為及影響範圍選擇檢查深度。權限、金流、資料遷移、對外契約、併發、安裝／更新與 CI／發布設定需要追查相關路徑；檔案小或只改設定不代表低風險。
- 確認失敗如何被偵測及恢復。需要說明回復時，分清撤回程式與復原資料／外部副作用；沒有證據不宣稱 rollback 可完全還原。

## 查找與驗證問題

- 從 diff 追查必要的呼叫者、型別、設定、測試與錯誤路徑。不要只憑命名、脫離上下文的一行或假設的未來需求報 bug。
- 為每個候選問題寫出觸發輸入／情境、執行路徑及使用者或系統影響，再找可支持或推翻它的證據。現有驗證或呼叫限制已排除該情境時，撤掉不成立的發現。
- 執行與風險相符的現有檢查或最小重現；先檢查命令的用途與副作用。不能執行時列出缺少條件，區分靜態推理、實際測試與尚未確認。
- 排版、命名偏好及未影響行為的清理交給既有 lint／formatter；使用者明確要求這類審查時再納入。舊問題與本次引入的問題分開，不把舊 bug 算給本次變更。
- 同一根因的多個症狀合併成一項，列出受影響位置與修正原則。合理但證據不足的疑點先查證，仍無法確定時列待確認，不包裝成確定缺陷。

## 輸出

先列重要發現；每項包含嚴重度、實際檔案與最小行號範圍、觸發情境、具體影響及證據。建議指出需修正的行為，不強迫作者採用唯一實作。

接著簡述已檢查範圍、實際執行的驗證、假設與剩餘限制。沒有確認問題時直接說明，不為湊數提出建議；測試通過或未發現問題都不是零風險保證。AI 的意見不替代專案要求的人工核准，也不授權合併、放寬保護或部署。

## 修正與複查如何收斂

- 新 commit 到來後，確認原問題是否消失，檢查新 diff 及受影響的相依路徑；大幅改寫、base 移動或新風險出現時才擴大範圍。先前證據只涵蓋當時版本。
- 對每項發現記錄「已修正、附理由不採納、待確認」，避免重複提出已處理內容；只有新證據才重開。
- 自動修正與審查反覆時，預設約三輪作為重新評估點，專案可另訂上限。到達上限仍未收斂，停止機械式來回，整理根因與剩餘風險、重新檢視方案；不能為過關自動關閉真問題或降低檢查。
- 修正已通過必要檢查後，不為可選偏好無限加輪。只有新失敗、新變更或具體未解風險才重跑相關驗證。

## 從漏網問題改善審查

專案已有回歸案例集或使用者要求建立時，把真實 bug／事故轉成可重現案例，記錄觸發條件、預期行為與缺少的檢查；敏感資料須去識別。既有測試能表達問題時優先用測試。

調整審查提示或工具時，用相同案例比較漏報、誤報與審查輪數；只做文字檢查就不能宣稱模型評測通過。不自動建立每日排程、值班制度或修改合併政策。
