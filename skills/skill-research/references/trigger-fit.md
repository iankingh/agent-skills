# 技能觸發適配與重疊檢查

當候選與現有技能功能接近，或使用者特別關心誤觸發、漏觸發與大量技能下的選擇時，依此檢查。這是採用前的適配評估；不自動安裝技能、執行測試或改造代理的路由系統。

## 比較使用者意圖與責任邊界

- 先比較候選與相關既有技能的 `name`、`description`，再讀取影響判斷的正文與支援檔。重點是使用情境、必要輸入、交付結果及容易混淆的排除範圍；不能只看關鍵詞重疊或描述長度。
- 檢查描述能否直接對上使用者的需求，把主要用途放前面，將詳細操作留在正文或按需參考。只列能避免實際誤路由的排除條件，不堆滿同義詞或所有無關任務。
- 有重疊時，說明是可共用一條流程、不同階段的互補技能，還是責任不清。建議沿用、分工或合併須有具體請求作依據，不因技能數量多就判定品質差。

## 用少量真實請求檢查邊界

為影響採用決定的候選，列出應觸發、同義改寫與近似負例。保留使用者實際會說的語句；研究階段可交付預期路由供審閱，不把它寫成已跑過的測試結果。

以下以技能研究為例，其他候選換成自己的任務：

| 請求 | 預期責任 |
| --- | --- |
| 找能把每週銷售資料變成報表的技能，先比較相依 | 技能研究與候選比較 |
| 這個 GitHub skill 能否處理我的報表？ | 評估指定候選，不為湊數擴搜 |
| 把我這套報表流程寫成 SKILL.md | 技能建立或修改；不是搜尋候選 |
| 安裝我已選好的報表技能 | 安裝流程；不是重新比較候選 |
| 將這篇報表技能介紹整理成筆記 | 內容整理；不自動研究或安裝 |

## 有實測需求時分層觀察

只有使用者要求或已授權測試時，才在允許的環境與資料範圍內執行；若只要求研究，提供測試建議即可。

- **可見性／召回**：技能是否已註冊，是否進入本次可用清單或候選集合；清單或內部檢索不可觀測時標示未知，不編造 Recall@K。
- **選擇**：正確技能已可見時是否被選用；明確點名與不提技能名的自然請求分開觀察。只靠明確點名成功，不能證明自動觸發正常。
- **執行與成果**：選對技能後，輸入、操作與最終結果是否符合任務；不能把缺參數、工具失敗或結果錯誤一律算成路由失敗。
- 依比較目的記錄誤觸發、漏觸發、完成情況與成本／延遲。比較前後使用相同案例，另留未參與調整的案例；說明樣本、分母與測試環境，不把小樣本寫成普遍準確率。

候選檢索、重排與領域分層是可選的系統設計，不是 Agent Skills 格式保證的內部行為；影片中的 Top-K 數字不作為固定規則。格式檢查或人工檢視只能支持靜態結論。
