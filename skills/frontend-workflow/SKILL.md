# 前端開發工作流

先確認使用者要交付的是畫面、規格、測試或審查意見，再選用下表對應的做法。若在既有專案工作，先讀最相近的頁面、共用元件或測試，沿用它的設計與程式慣例。各項做法可獨立使用。

| 任務 | 做法與交付 |
| --- | --- |
| 決定畫面方向（Frontend Design） | 找出這個畫面上最重要的使用者動作，再決定資訊順序、字級與留白。例如訂單列表會被反覆掃讀，讓金額對齊、狀態易辨，比加強頁首裝飾更有助於找出異常訂單。要求實作時，把選擇落實在頁面上。 |
| 建立一致的視覺規則（UI UX Pro Max） | 先找專案既有的色彩、間距與元件樣式。需要新增規則時，依用途命名並套用到實際狀態，例如錯誤欄位同時顯示說明文字與錯誤色。從寬螢幕切到窄螢幕，確認主要操作仍可見、可用。 |
| 定義元件規格（Frontend Spec） | 從呼叫端寫一個最小使用範例，再定義輸入、事件與狀態由誰管理。使用 TypeScript 的專案附上 props 與事件型別。對非同步元件，分清首次載入、查無結果與請求失敗，寫明每個狀態可執行的操作。 |
| 補前端測試（Test Gen） | 依既有測試框架，把規格轉成「做了什麼、應看到什麼」。優先測會改變使用者結果的分支，例如搜尋失敗後按重試應保留篩選條件。模擬網路等外部邊界，保留元件本身的互動，執行對應測試並回報結果。 |
| 審查前端變更（Code Review） | 由 diff 找出受影響的操作，沿事件、狀態更新與畫面回饋檢查；依改動選擇鍵盤操作、快速連點或窄螢幕等情境。每項問題附檔案位置、觸發條件與可觀察的影響，並交代哪些情境已實跑。 |

例如使用者只要「可排序表格的元件規格」，交付呼叫範例、排序狀態的擁有者，以及點擊或用鍵盤啟動欄首後的預期行為即可。如果要求把排序做完，沿用同一組行為實作，再用測試確認列順序與欄首的排序狀態一致。
