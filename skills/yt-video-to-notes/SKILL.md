# 🎬 YouTube 影片／播放清單轉資料夾筆記

以使用者提供的影片或清單為來源，整理繁體中文、台灣用語的 Markdown 筆記。主題不限技術；一般資料夾即可使用。只有要求寫入或對話已確認目的地時才建立檔案；僅要求摘要時在對話交付。

## 1. 判斷輸入與目的地

- **單支影片**：`watch?v=...`、`youtu.be`、Shorts、live 等以影片 ID 識別，一支一篇。即使附帶 `list=WL`、其他 `list` 或 `index`，仍只處理該支，除非使用者明確要求整份清單。來源記錄為 `https://www.youtube.com/watch?v=影片ID`。
- **播放清單**：純 `playlist?list=...` 連結或明確要求整份清單時，取得實際順序、影片 ID、標題及要求集數，建立一個總覽與多篇章節。依原章節編號（如 4.1、4.2）及主題分組，每篇約 4～9 集為參考，章節邊界與使用者粒度優先。
- **私人清單／稍後觀看**：不可讀時依可用工具的登入流程處理，或請使用者提供可存取的清單／單支影片；不推測內容，也不自行更改公開設定。保留私人、已刪除與無法取得的項目，不把可見項目數冒充全清單。
- **目的地**：先採用指定或已確認的資料夾，讀適用的 `AGENTS.md` 與既有結構。一般根目錄預設寫入 `影片筆記/`；已指定影片筆記目錄時直接使用。只有確實無法判定目的地才詢問，不假設私人筆記庫路徑。
- **查重**：在目標目錄以影片 ID 查既有 Markdown，標題僅輔助；同來源才比較是否更新，保留使用者註記與原建立日期。已刪除的筆記可重建；不同 ID 或不同原文稿不因標題相近而覆蓋、合併。

建立前讀 [資料夾與連結規則](references/folders.md)。預設一般 Markdown，相對連結含 `.md`；只有明確指定 Obsidian 時讀 [Obsidian 規則](references/obsidian.md)。本流程不使用 Notion 資料庫、mention、建頁 API 或 `edit_reference`。

## 2. 依序取得內容

先確認實際可用的連接器、字幕、媒體與瀏覽器工具，遵守各工具範圍。不假設 `/data/...` 腳本、瀏覽器注入 API 或語音模型存在。需要音訊或分段閱讀時，讀 [媒體取得與驗證](references/media.md)。

1. **中繼資料**：核對原標題、頻道／講者、發布日期、長度、說明欄與章節。可用 YouTube oEmbed 取標題／頻道，再由頁面或媒體工具補其他欄位；觀看數、讚數與訂閱數僅在可取得且有用途時記錄，標明查核日期。影片標題年份不等於頁面發布日期。
2. **字幕**：優先使用可取得的人工或自動字幕，記錄語言、來源方法與實際範圍。以時間區間分段閱讀至要求範圍結尾，避免長輸出截斷；重要圖表、程式碼、數字與辨識疑點用實際畫面或說明欄核對。
3. **無字幕**：取得音訊，先通過下節的長度與內容抽查，再使用可用的語音辨識工具。SenseVoice + Silero VAD 是可選方案，須先確認相依、模型與指令；不把不存在的 `sv.py` 當成已提供工具。批次長任務保留程序識別、log 與各集狀態，可先整理已轉完的章節。
4. **備援**：YouTube 不可讀時，可查同課程的 Bilibili 等版本；逐集核對講者、主題、內容與對應分 P，建立「YouTube 集數 → 備援來源／區間」對照，不假設集數或時間軸相同。不用其他教材補成原影片內容。
5. **仍不完整**：保留已取得的實質內容與缺口。若採畫面／圖卡摘要，明記沒有完整聽辨；只有來源、標題或大綱時標待整理，不捏造講者論點、引述或時間戳。評論不是作者正文。

## 3. 音訊驗證與來源完整性

- **實際長度**：以 `scripts/sources.py audio` 計算 WAV 實際樣本長度，其他格式用 ffprobe，再與影片片長比對。過短、過長、空檔或截斷檔先查漏抓、重複、廣告或自動播放下一支；擷取程式的成功訊息、檔案存在及播放器進度都不足以證明有效。
- **排除廣告**：先試讀開頭轉錄，再抽查中段與結尾，核對語言、主題、講者及畫面。語言相同或長度相符仍不能證明內容正確。誤抓素材隔離並標無效，不作成功來源；重播或接續下一支時，只保留已核對的目標時間軸。
- **逐集記錄缺口**：記錄要求範圍、來源類型（字幕／音訊語音辨識／已核對備援／畫面摘要／未取得）、實際涵蓋與未取得區間、失敗原因。筆記與總覽都揭露缺口，最後回覆同步說明。VAD 靜音與未取得片段分開判斷，不把沒有語音的空白自動當成遺失。
- **時間與補充**：時間戳只取自已核對時間軸。備援時間未對齊時連到實際備援並說明，不虛造 YouTube 定位；自己的外部補充標「（筆記補充）」並附來源，不因此宣稱影片完整。
- **保存工具**：實際使用並測試過的擷取、轉檔、辨識、分段閱讀及連結工具，依 [保存與還原規則](references/media.md#保存與還原工具) 保存程式、指令、需求、模型來源及驗證紀錄。尚未打包或還原測試的部分明示，不宣稱可直接重用。

## 4. 筆記內容與寫作

新整理或明確重整時讀 [筆記結構](references/note-structure.md)，依序整理：核心結論、影片／章節介紹與來源、架構表、主要內容、有依據才收錄的關鍵引述、總結、概念表、行動清單及資源。

核心結論用一般段落 1～2 段，不用 callout；標題保留講者與原意，正文配合適的 emoji。重點使用 Markdown 粗體；程式碼、檔名用反引號，時間戳不放進程式碼區塊。行動清單對準影片對象，未提到期限就不補。主題不限技術，不強加面試、程式工具或人生 RPG 內容。

一律繁體中文、台灣用語；引用、程式碼、專有名詞與指定標題保留原意。數據、成效與經驗寫成「影片提到／講者表示」；業配段落不收進內容筆記。語音錯字依上下文修正，無法核對的數字、名詞與引述明記疑點。自己的練習、延伸閱讀及技術新版本差異均標「（筆記補充）」；新版本以官方文件查核，不把例子視為最新。

## 5. 建立檔案與驗收

讀 [工具指令](references/tools.md)。單支影片建立一篇 `.md`；播放清單建立獨立資料夾的 `README.md` 與 `章節/`，總覽含介紹、實際集數、學習路線（筆記補充）、章節索引與來源缺口。章節可往返總覽，未建立項目不放失效連結。

- 長內容先寫工作區草稿，再以 `scripts/build.py render` 轉換時間戳與相對 Markdown 連結，輸出另一個檔案；Obsidian 才使用其連結模式。建立前用 `scripts/chk.py` 檢查新寫內容，人工判讀候選與誤報；缺依賴時明記檢查未完成。
- 章節逐篇驗收後用 `build.py record` 記到輸出筆記目錄外的本批 `created.txt`。續作先 `build.py check`，查檔案雜湊、來源與缺集；同時核對真實清單與來源涵蓋，不能只靠機器紀錄宣稱完整。
- `完成` 表示要求範圍的內容已取得、讀取並整理；僅有畫面摘要不等同已完成整片內容，除非原任務就是畫面摘要。`待補充` 表示仍缺主要內容、集數或重要核對；`待整理` 表示只有來源與基本資料。保留實際缺集，不刪掉要求範圍來讓檢查通過。歸檔、內容完整性與使用者學完分開記錄。
- 正文的來源查核段落記錄本次實際閱讀方法、涵蓋範圍與缺漏。更新既有筆記時，區分前次查核與本次新增的查核結果。
- 音訊、字幕、映射、log 與進度放工作區；不放憑證、登入資料或無關音訊進共用技能。修改與清理沿用授權及目標規則，不搬動無關筆記。

只有明確要求原文匯入時，保留原標題、正文、程式碼、來源及既有閱讀限制，不重新摘要或套模板；逐位元保留以 SHA-256 核對，必要的屬性或連結轉換另驗證，保留原始來源檔。

## 6. 交付

繁體中文回覆，先放本次筆記與總覽的可點擊絕對路徑，再簡述重點。列出建立／更新檔案及實際使用的字幕、語音辨識、備援或畫面方法，揭露時間戳限制、未涵蓋區間／集數與仍需核對項目；不宣稱看過未取得的內容，也不保證每支影片都能取得字幕。
