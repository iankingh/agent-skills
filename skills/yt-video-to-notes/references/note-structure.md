# 新影片筆記：結構、寫作與課程流程

只在新影片整理或使用者明確要求重整內容時讀本檔。已整理文稿的原文匯入不套用模板、繁簡轉換或下列建置流程。

## 標題與圖示

使用者已提供完整標題時原樣保留；需要產生標題時使用：

| 類型 | 標題 |
| --- | --- |
| 單篇 | `講者-主題｜重點、重點（筆記）` |
| 同系列單集 | `講者-主題 第 N 集｜重點（筆記）` |
| 課程章節 | `課程簡稱 NN｜章節主題：重點、重點（筆記）` |
| 課程總頁 | `講者或機構｜課程名 N 集課程筆記` |

講者使用已確認的講者名或頻道名。新筆記正文使用 `# 合適的 emoji 完整標題`；圖示不取代標題、不加入原文匯入稿。檔名依 [資料夾規則](folders.md) 或目的地既有命名；`▶️ YT-` 前綴只在採用此慣例的 Obsidian 目的地使用。N 使用已確認的集數；僅整理部分時明示實際範圍。

## 單篇與章節筆記的順序

章節內文依題材決定長度，不灌水。下列區段依序呈現；來源不足時寫明限制，不為填滿模板造出觀點、時間或程式碼。

1. **`## 核心結論`**：一般段落 1～2 段，不使用 callout。先說影片主要結論，再說做法、適用條件與仍需人工判斷之處；關鍵字加粗。

2. **`## 這部影片是什麼`**：第一行放 `### 來源：[影片標題](原影片網址)`，連結文字保留影片標題。接著說明想回答的問題、核心觀點、適合誰，以及業配、地區用語、時效性等實際注意事項。
   - 章節改用 `## 這個章節是什麼`，並說明涵蓋第幾集至第幾集、案例與想回答的問題。
   - 多集章節逐集列來源，不拿播放清單標題冒充單支影片標題。
3. **`### 影片架構`**：表格欄位為「時間（或集數）｜段落｜重點」。
4. **內容段落**：在段落標題或個別重點後放有依據的時間戳 `[m:ss](https://www.youtube.com/watch?v=ID&t=秒數s)`，程式碼區塊不插入時間戳連結。跨集必須能辨識影片與集數。條列使用「**粗體小結**：說明」。技術課保留關鍵程式碼、設定檔和比較表；自行重建的示意標為「（筆記補充）」並註明未執行或實際測試範圍。
5. **`## 關鍵引述`**：僅有值得記且可核對的原話時寫 1～3 則引用，並說明意義；語音辨識錯字可修順但不改意義，不把自己的改寫加上引號冒充原話。
6. **`## 總結`**：收斂主要論點及適用條件，不重複整篇正文。
7. **`## 關鍵概念`**：表格欄位為「概念｜一句話解釋」。
8. **`## 快速上手：行動清單`**：使用 `- [ ]`，依影片對象標示適用角色；影片未提到期限就不補期限。技術課需要時加入「（筆記補充）新版本差異」，引用查核當日官方文件；Spring Boot 3、Jakarta 只是例子，不固定視為最新。工程師練習、面試或人生 RPG 僅在使用者要求且題材相關時補充，不代為執行或發放 XP。
9. **`## 資源`**：原影片、說明欄的相關來源、實際存在的工作區筆記，以及標示「（筆記補充）」的延伸閱讀。一般資料夾用相對 Markdown 連結，Obsidian 才用其既有連結格式。多集章節保留各集可點擊連結。

在「這部影片是什麼」或「資源」中加入來源紀錄：每集的來源類型、實際閱讀區間、缺口與原因，詳見 [媒體驗證規則](media.md)。不將筆記已建立、影片內容完整性與使用者學完混為一談。

## 寫作規則

- 一律繁體中文、台灣用語，例如面向對象→物件導向、事務→交易、異常→例外、數據源→資料來源、接口→介面、視頻→影片、立 flag→許下目標；依語境判斷，原始程式碼、專有名詞、引用及使用者指定標題不機械替換。
- 重點使用標準 Markdown `**粗體**`；程式碼和檔名加反引號。內部連結使用實際存在、可唯一定位的筆記；交付訊息用絕對路徑 Markdown 連結。主題不限技術，不強加工程師情境到生活或語言題材。
- 自己新增的觀點、練習、模板、版本差異及延伸閱讀一律標「（筆記補充）」。有疑問的名言作者或出處需加一句說明；未驗證的原稿說法不改寫成已查證。
- 業配段落不收進內容筆記，來源涵蓋紀錄可標明略過範圍。影片數據、成效與經驗保留「影片提到／講者表示」的歸屬。語音辨識錯字依上下文修正；不確定數字、術語用畫面或說明欄核對，仍無法確認時明示。
- 建立前執行 `scripts/chk.py`，逐項看疑似簡體字、台灣用語與誤報提示。峰、秘、游、台、里、群、吃、占、托、干、床常有誤報，不因出現在清單就一律改字或略過上下文。
- `chk.py` 只報告、不覆寫檔案，也不能證明文章語意正確。缺 OpenCC 時回報檢查未完成，不能把沒有執行當成通過。

## 明確要求的播放清單

1. 先取得使用者要求範圍的清單順序、每集標題與影片 ID，記錄無法讀取、私人或已刪除項目。普通單支連結帶 `list`、`index` 不展開清單。依原章節編號（如 4.1、4.2）及主題分組，每篇約 4～9 集為參考，章節邊界與使用者粒度優先，短清單不硬拆；非課程清單依實際主題分組。同課程備援逐集核對對照。
2. 依 [資料夾規則](folders.md) 或明確指定的 Obsidian 結構建立總覽：介紹、要求與實際涵蓋集數、來源缺口、標「（筆記補充）」的學習路線及 `## 章節索引`。未建立章節標「待整理」，不放失效連結；已完成章節可先連結，整份清單仍維持待補充。
3. 長內容先寫草稿 Markdown，使用 [tools.md](tools.md) 的 `build.py` 轉換時間戳和連結。只有取得內容的章節才能撰寫；若可使用背景轉錄工具，同時處理已完成轉錄的章節並保留其範圍紀錄。
4. 每篇經內容、來源、繁中與連結檢查後，以 `build.py record` 記入本批次的 `created.txt`。這份機器紀錄放在輸出筆記目錄外的本批工作區，使用絕對路徑、集數、來源與 SHA-256，不把草稿當成已完成。缺集不能從要求範圍移除以求通過；來源紀錄另保留取得區間與缺口。續作未完成前保留紀錄。
5. 續作先執行 `build.py check`：已完成且內容相同的章節跳過；缺集或失效紀錄逐項處理。人工重新核對已修改章節後才能再次 `record`。
6. 索引使用「#｜筆記連結｜集數｜主題｜狀態」，一般資料夾用相對 Markdown 連結並可往返總覽；實際來源缺口另列。全部要求範圍已整理且主要內容有來源時才標完成；工具紀錄一致不證明遠端清單或內容完整，課程歸檔不代表使用者已學完。

## 交付

繁體中文回覆，先放筆記與總覽的可點擊絕對路徑連結，再簡述重點、字幕／語音辨識／畫面等方法、時間戳誤差與未涵蓋範圍。列出本次建立或更新的檔案，不回傳 Notion mention 或 `edit_reference`。
